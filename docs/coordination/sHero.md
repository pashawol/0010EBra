# sHero — координация

Блок: `source/pug/blocks/sHero/*`, данные `source/pug/data/sHero.json`, картинки
`source/img/sHero/*`, dev-страница `source/pug/pages/dev-sHero.pug`, тест
`tests/blocks-sHero.test.js`. Node `161:134` (десктоп 1920×1080).

## 1. Заявка: баг в `eb-ui.pug` — `+ebBtn` / `+ebIconBtn` дублируют базовый класс

**Не исправлял сам** (общий файл, не в моей зоне). Воспроизводится ЛЮБЫМ
вызовом `+ebBtn(...)` или `+ebIconBtn(...)` (а значит и `+ebSliderNav()`,
которая вызывает `+ebIconBtn` внутри) — html-validate ловит `no-dup-class`:

```
<button class="eb-btn eb-btn eb-btn--primary" ...>
<button class="eb-icon-btn eb-icon-btn eb-icon-btn--solid ..." ...>
```

Причина: миксины делают `+b.BUTTON.eb-btn(class="eb-btn--" + mode ...)` —
модификатор передан **сырой строкой** в атрибут `class=""`, а не bemto-чейном
(`.eb-btn--` + mode как отдельный `.`-класс). bemto в `+b` не распознаёт такую
строку как «модификатор предыдущего объекta» и добавляет базовый класс блока
ещё раз поверх. Уже ловил `dev-sProcess.html` (eb-icon-btn) и
`dev-sBlog.html`/`dev-sExpertise.html` (eb-btn/eb-icon-btn/eb-slider-nav) —
это НЕ баг, специфичный для sHero, это баг самого компонента, задевает всех
потребителей.

**Локальный воркэраунд в sHero** (без правки `eb-ui.pug`): кнопки и
слайдер-навигацию я не вызываю через `+ebBtn`/`+ebSliderNav`/`+ebIconBtn`, а
пишу разметку вручную 1:1 с тем же контрактом классов (`eb-btn eb-btn--mode`,
`eb-icon-btn eb-icon-btn--solid`, `eb-slider-nav__prev.swiper-button-prev` и
т.д.) — стили те же самые (SCSS токенов не трогал), просто без дубля класса.
См. `_sHero.pug`, блоки `.sHero__buttons` и `.sHero__nav`.

**Предлагаемый фикс для координатора** (правка `eb-ui.pug`, 2 мест):
```pug
// было
+b.BUTTON.eb-btn(class="eb-btn--" + mode type="button")&attributes(attributes)
// стало (bemto-модификатор чейном, а не строкой)
+b.BUTTON.eb-btn._{mode}(type="button")&attributes(attributes)
```
(и аналогично в `ebIconBtn`). После фикса дев-страницы `sProcess`/`sBlog`/
`sExpertise`/мою можно будет вернуть на настоящие `+ebBtn`/`+ebSliderNav` —
я специально оставил комментарии-указатели в `_sHero.pug`, где именно
заменить обратно.

## 2. Заявка: `+e.DIV.swiper-wrapper` ломает Swiper — грабля для всех блоков со слайдером

Не баг компонента, а моя собственная грабля на старте, фиксирую для других
блоков-потребителей Swiper (`sReels`, `sCollection`, `sExpertise`,
`sBestSets`, `sFavorites`, `sStory`): **`+e.DIV.swiper-wrapper` — НЕЛЬЗЯ**.
bemto-миксин `+e` всегда навешивает BEM-префикс блока, поэтому получится
`sHero__swiper-wrapper` вместо служебного `swiper-wrapper`, который требуют
CSS/JS Swiper. Итог — секция «схлопывается» в высоту 0 и слайд-фото визуально
пропадает (хотя в DOM оно есть и декодировано — классическая «есть в DOM, не
видно на скриншоте»). Поймал это именно скриншот-сверкой (первый прогон дал
плоский бордовый фон без фото). Нужно писать **plain-класс**:
```pug
.swiper-wrapper
	each slide in data.slides
		+e.DIV.slide.swiper-slide
```
(`.slide.swiper-slide` — можно мешать BEM-элемент с литеральным классом,
проблема именно когда литеральный класс — ЕДИНСТВЕННЫЙ аргумент `+e`).

## 3. Мобильного макета `sHero` в Figma нет — адаптация моя

`692:1129` («[Mobile] Home Page») начинается сразу с секции «Кому помогает
Esthetic Bra» (frame `710:1466`, y=20) — хиро-блока среди детей НЕТ. Нашёл ещё
один узел с именем «[Mobile] Home Page» (`683:1036`) — это пустой фрейм
375×760 без единого child, то есть заглушка/недоделанный черновик, не
финальная вёрстка. Нода `777:28` «[Mobile] Fix header» тоже не хиро — там по
ошибке вложена копия контента Section 2 (баг самого макета/инстанса
компонента), полезного для хиро там тоже нет.

**Решение:** мобильная адаптация — моя, mobile-first, без попапа хотспота
(`display:none` до `xl`, чтобы не перегружать узкий экран текстом без
уточнённой дизайн-позиции), заголовок+текст+кнопки в обычном потоке (flex
column, `justify-content:flex-end` в стадии `100svh`), декоративное
«навсегда» и пара стрелок — внизу компактным блоком. Точная 1:1 копия
композиции макета (проценты от 1920×1080) применяется только с брейкпоинта
`xl` (1200px) — ширины между этим и мобильным потоком не пытаются
интерполировать абсолютные координаты.

Если у Pavel/дизайнера появится мобильный кадр хиро — пересобрать
`&__hotspot`/`&__nav`/расположение декора под него, текущее — осознанный
компромисс, не финал.

## 4. Хотспот — без круглого фото-аватара из макета

В `161:144` («Mini Card / Link») у точки есть 64×64 фото-аватар (`Frame731`)
поверх обычной dot+card карточки. Компонент `+ebHotspot` (используется также
в `sFitting`, `sCollection`) — это универсальный dot (24px CSS-круг) + card,
без слота под аватар. Чтобы не форкать общий компонент под один блок (и не
плодить дубль по DoD «переиспользование»), я **сознательно не стал** добавлять
фото-аватар и использую `+ebHotspot('Коллекция', 'Asoka Mia Dot', '#')` как
есть — контент карточки (заголовок/текст/стрелка) 1:1 совпадает с макетом,
только без декоративного кружка-фото сверху. `hero-collection-thumb.jpg` не
понадобился, удалил из `source/img/sHero/`.

Если координатор решит добавить аватар-слот в `+ebHotspot` централизованно —
у `sFitting`/`sCollection` может быть аналогичная польза (см. PLAN §4: «3
разных блока — один компонент»).

## 5. Разметка dots+arrows одним блоком (не по разным углам, как в макете)

В `161:134` пагинация — низ-лево (`x=65,y=1010`), стрелки — низ-право
(`x=1765/1822,y=988`). Атом `.eb-slider-nav` (используется 6+ блоками) —
единая строка `justify-content:space-between`, с растяжкой на всю ширину
контейнера это визуально даёт тот же эффект (точки прижаты к левому краю,
стрелки — к правому), но на деле я расположил `&__nav` компактным блоком в
правом нижнем углу (см. скриншот-сверку) — не растянул на всю ширину
`.container`, чтобы не создавать пустую полосу поперёк фото. Отличие от
макета: точки не у левого края экрана. Осознанный компромисс ради чистой
композиции; можно поправить (растянуть `&__nav` на 100% ширины контейнера),
если ревизор сочтёт критичным.

## 6. Full-bleed грабля (§3.1 плана) — проверена, не применима

`.sHero` — секция верхнего уровня (не внутри `.container`), поэтому
`eb-bleed()`/`eb-bleed-reset()` не нужны: слайдер и так занимает 100% ширины
вьюпорта без каких-либо трюков. Фиксирую специально, чтобы ревизор не решил,
что грабля пропущена по невнимательности.
