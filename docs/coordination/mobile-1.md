## Находка: sHero отсутствует в мобильном макете

Мобильный фрейм `692:1129` начинается СРАЗУ с sAudience (`710:1466` на y=20) —
никакого Hero-узла перед ним нет (проверено скриншотом верхних ~2300px
фрейма и текстовым поиском по заголовку `sHero` "Влюбиться в себя...
навсегда" — совпадений в поддереве `692:1129` нет). Десктопный Hero с этим
текстом существует (canvas `0:1` → `1:202` → `1:557`/`1:564`), но отдельного
мобильного Hero-кадра в файле нет.

Живая реализация `sHero` при этом существует и выглядит внутренне
целостной (слайд, заголовок, CTA, hotspot) — я её НЕ трогал, сверять не с
чем. **Нужно решение заказчика/дизайнера**: либо мобильный Hero
действительно не предусмотрен макетом (тогда текущая реализация — лучшее
приближение по аналогии с десктопом, оставляю как есть), либо в Figma
недостаёт кадра и его нужно домakeтить. Прошу координатора уточнить у
заказчика/дизайнера и завести мобильный Hero-фрейм, если он предполагался.

## Найденные расхождения — почини́л

### 1. sReels — порядок интро и слайдера перепутан (мобиль)
**Было:** DOM-порядок клал `.container.sReels__overlay` (тег «Примеры» +
заголовок + сабтайтл + пагинация) ПОСЛЕ `.track` (слайдер) — на мобиле, где
`.sReels__overlay` рендерится в обычном потоке (не абсолютно, это включается
только с `lg`), это визуально ставило текстовый блок НИЖЕ слайдера. В
макете (`721:2`) порядок обратный: тег → заголовок → сабтайтл → слайдер.
Комментарий в самом же `_sReels.scss` ("на мобиле текст стоит НАД
слайдером") уже фиксировал правильное намерение — разметка ему не
соответствовала.
**Стало:** переставил блок `.container.sReels__overlay` перед `.track` в
`_sReels.pug`. На десктопе не влияет: там `.sReels__overlay` —
`position: absolute; inset: 0`, порядок в DOM для абсолютно
спозиционированного элемента визуально не важен (в стеке различает
`z-index`, который уже был `2`). Проверил оба брейкпоинта (375 и 1920) —
десктоп не сломался.
Файлы: `source/pug/blocks/sReels/_sReels.pug`.
Тест: обновил `tests/__snapshots__/blocks-sReels.test.js.snap` (`-u`,
затронут только этот файл снапшотов).

### 2. sTransformIntro — метки шли потоком под заголовком вместо "вокруг" него
**Было:** на мобиле `&__tag` был `position: relative` (обычный поток), три
метки («Реальные истории» / «Фото/Видео примеры» / «Отзывы») рендерились
одна под другой ПОД заголовком общим столбцом. В макете (`710:1925`) метки
расположены вокруг заголовка: одна выше, две — ниже по разным сторонам (не
единой колонкой). Комментарий в шапке файла ("вокруг плавающие метки") уже
описывал это намерение, комментарий у мобильного правила прямо объяснял
компромисс ("иначе наезжают на текст") — т.е. это был осознанный, но
расходящийся с макетом компромисс, не забытая доработка.
**Стало:** сделал метки `position: absolute` на мобиле тоже (координаты —
своя раскладка, не буквальный перенос % из Figma, см. ниже "почему не %"),
заголовок отцентрирован в той же координатной плоскости. Числом проверил
пересечения боксов (`getBoundingClientRect`) заголовка и всех трёх меток —
`overlapsWithTitle: [false,false,false]`, наложений нет ни на одной из них.
Десктопная раскладка (`≥lg`) не менялась по существу, кроме одного
попутного фикса ниже.

**Побочный технический фикс (общий для обоих брейкпоинтов):** `&__inner`
имел только `min-height` — а проценты `top`/`bottom` у `position:
relative`/`position: absolute` потомков резолвятся от containing block
только когда его высота "definite"; `min-height` для этого не считается
(проверил числом: `top: 50%` у заголовка резолвился в `0`, а не в половину
высоты контейнера — `getBoundingClientRect` показывал заголовок почти у
верхнего края вместо центра). Заменил/дополнил на явный `height` на обоих
брейкпоинтах (`rem(230)` мобиль, `rem(300)` десктоп, `min-height` оставлен
рядом для отказоустойчивости, если контент когда-нибудь станет выше). Это
меняет только резолюцию процентов, к самим числам десктопных `top`/`left`/
`bottom` не притрагивался, десктоп-скриншот сверил визуально — не
изменился.

**Почему координаты меток не буквальный перенос % из Figma-кадра
(`710:1925`, 538×496):** высота реализации (230px) не масштабируется
пропорционально высоте Figma-кадра относительно РЕАЛЬНОЙ высоты типографики
(шрифт/паддинги тега не сжимаются вместе с "высотой макета") — буквальный
перенос % давал те же 3–6px наложения тега на заголовок. Расположил метки в
`rem()` (пиксельно), сохранив тот же композиционный смысл (одна выше
заголовка, две — ниже по разным горизонталям), с зазором, подтверждённым
числом, а не на глаз.

Файлы: `source/pug/blocks/sTransformIntro/_sTransformIntro.scss`. Pug не
трогал (модификаторы `--a/--b/--c` уже передавались верно).

### 3. sStory — дефолтный "peek" компаратора до/после показывал пустой фон
**Было:** `source/img/sStory/before.jpg` — full-body фото 1088×1088, где
модель занимает примерно правую треть кадра (руки/лицо в верхней части, но
переносится в кроп `object-position: bottom`, который показывает нижнюю
часть, где модель ещё правее). Бокс компаратора (`345×275`, "cover"
масштаб = width-bound, без запаса по горизонтали для сдвига через
`object-position-x`) при дефолтном `data-split="30"` показывал именно ЛЕВЫЕ
~30% этого фото — а там сплошной бежевый фон, а не силуэт модели. В макете
(`700:2046`/`218:361`) на том же 30%-пике виден кусок модели (тёмный
бюстгальтер/плечо) — т.е. составлено под конкретный сценарий "peek".
Числом подтвердил: `naturalWidth`/`complete` у `<img>` в норме, проблема не
в загрузке, а в композиции кадра относительно бокса (сверил кроп `(0,222,
330,1088)` — сплошной фон без единого пикселя силуэта).
**Стало:** обрезал `source/img/sStory/before.jpg` слева (убрал пустую фоновую
полосу, `crop(350, 0, 1088, 1088)` → 738×1088), пересобрал (`npm run build`
регенерирует `public/img` из `source/img`). После фикса дефолтный 30%-пик
показывает силуэт модели (бедро/бюстгальтер), полный reveal (100%) —
модель занимает почти всю ширину кадра, тоже ближе к макету. Второй
слайд («Александра», временная заглушка, переиспользует те же файлы, задокументирована
в `docs/coordination/sStory.md` предыдущим автором) получил тот же фикс
автоматически.
Файлы: `source/img/sStory/before.jpg` (переписан).

**Не мой контент-косяк, но стоит знать:** `before.jpg` и `after.jpg` — фото
РАЗНЫХ моделей (разные лица/позы/цвет волос), не пара до/после одного
человека. Кроп исправил композицию (силуэт виден в нужном месте), но
семантическое рассогласование "разные женщины" — вопрос реальной
фотосъёмки, не чинится кодом/кропом. Не заявка координатору (это уже за
пределами вёрстки), просто фиксирую для протокола.

## Проверено и БЕЗ расхождений
- **sAudience** — состав карточек, порядок, фон, виджет-аватарки — совпадает
  с макетом почти пиксельно.
- **sFitting** — хотспоты, стрелки, фото, факт-карточка «80%» — совпадает.
  (Ложная тревога в процессе: факт-карточка показалась "невидимой"
  `visibility:hidden` при скриншоте без докрутки — это ожидаемая
  scroll-reveal анимация (`anim.js`, вне моей зоны), триггерится по
  `ScrollTrigger` при реальном скролле; после докрутки видна и совпадает.)
- **sProcess** — шаги 01/02/…, видео-виджет «О брафиттинге» — совпадает.
- **sExpertise** — фото, заголовок, факт, слайдер-стрелки — совпадает
  почти пиксельно.
