# sReels — координация

Блок «Когда белье меняет жизнь навсегда» (node `321:1063` desktop / `721:2`
mobile, часть `692:1129`; карточка-образец `669:3819 Video (Preview)`; попап
просмотра `682:238` — попап не строил, см. компромисс ниже).

> **Актуально на 2026-08-17.** Механизм попапа переделан: карточки больше не
> используют `data-fancybox` / `data-src`, а несут `data-video-modal="<id модалки>"`
> и `data-video-index="<N>"`. Разметка модалки — общий миксин `+videoModal()`
> (`source/pug/blocks/mixin-wrap/components/video-modal.pug`), стили —
> `source/pug/blocks/video-modal/_video-modal.scss`, логика —
> `source/js/video-modal.js`: он сам вызывает `Fancybox.show()` с профилем
> `mainClass: 'fancybox--video'`, поднимает Swiper (coverflow) после показа
> модалки и перематывает его на индекс нажатой карточки. Отдельный
> `Fancybox.bind()` в `JSCCommon.js` не нужен и удалён. Разделы ниже описывают
> прежнюю реализацию и оставлены как история решений.


## Заявки координатору (общие файлы, сам не трогал)

0. **[РЕШЕНО координатором, два захода]** Вложенная dev-страница
   (`source/pug/pages/dev/sReels.pug` → `public/dev/sReels.html`)
   промахивалась по относительным путям ассетов (`libs/...`, `css/...` в
   `js-css.pug` рассчитаны на страницу в корне `public/`) — сплошной 404 на
   css/js/svg, `swiper`/`Fancybox` не грузились, постеры не декодировались
   (`naturalWidth` = 0), проверено Playwright.
   - Первый вариант координатора (`- var baseHref = '../'` в `block
     variables` + `if typeof baseHref !== 'undefined'` в head `main.pug`) не
     сработал: `block variables` в `main.pug` стоит ПОСЛЕ head, Pug-шаблон —
     одна JS-функция с последовательным исполнением, `var` хостится, но
     присваивается только при исполнении своей строки — в момент проверки
     `typeof baseHref` в head значение ещё `undefined`. Подтвердил грепом:
     `<base>` в собранном HTML отсутствовал.
   - Сообщил координатору диагноз, он поправил `main.pug` на независимый от
     порядка **Pug-блок** (`block base`, переопределяемый на месте). У себя
     заменил на:
     ```pug
     block base
     	base(href="../")
     ```
     Проверил: `<base href="../">` появляется в `public/dev/sReels.html`,
     ассеты грузятся, Swiper инициализируется, `naturalWidth > 0` у постеров.

**`source/js/JSCCommon.js` — нужен второй профиль `Fancybox.bind()` для
группы `"sReels"`.**

Сейчас `JSCCommon.modalCall()` вызывает `Fancybox.bind()` только для
`'[data-fancybox="modal"], .link-modal-js'`, и следом вешает СВОЙ
`document`-обработчик клика на тот же селектор, который делает
`document.querySelector(element.dataset.src)` без try/catch (строка ~71).
Карточки sReels **намеренно** используют `data-fancybox="sReels"` (не
`"modal"`), чтобы не попасть под этот обработчик — если бы использовалась
группа `"modal"`, `data-src="#sReels-video-0"` тоже сработал бы с
`querySelector` (это валидный id-селектор), но при следующей правке кто-то
мог бы сменить `data-src` на прямой URL видео и словить необработанное
исключение в общем клик-хендлере на всей странице. Разделение групп — это
защита от такого будущего сценария, а не обход текущего бага.

Нужно добавить в `JSCCommon.js` (по образцу `modalCall()`, вызвать рядом,
например `JSCCommon.reelsCall()`):

```js
static reelsCall() {
	Fancybox.bind('[data-fancybox="sReels"]', {
		groupAll: false,
		dragToClose: false,
	})
}
```

и вызов рядом с `modalCall()` в `init()`. Для локальной QA-проверки я
временно продублировал этот вызов инлайн-скриптом в
`source/pug/pages/dev/sReels.pug` (`block scripts`) — он не трогает
`JSCCommon.js`, только проверяет, что механика Fancybox 6 (`Fancybox.bind`
+ `data-fancybox` + `data-src` на скрытый `id`) реально открывает попап.

## Компромиссы / отклонения от буквального макета

1. **Реального видео нет** (решение зафиксировано в PLAN §1: «Постер в
   карточке, по клику — плеер в Fancybox»). Каждая карточка несёт
   `data-fancybox="sReels"` + `data-src="#sReels-video-N"`, указывающий на
   скрытый `div(style="display: none")` с `<video poster="..."><source
   src="" type="video/mp4"></video>`. Заказчику остаётся подставить
   `src` в `<source>` — верстать заново не нужно. Не использовал реальный
   внешний URL видео специально: тесты и dev-стенд должны быть
   детерминированными и не зависеть от сети.

2. **Единая пропорция карточки для всех слайдов** (438×660 из
   карточки-образца `669:3819`), а не увеличенная геометрия первого
   слайда в `321:1063` (590×740, другая пропорция — это featured-версия
   именно в композиции секции). Так проще для Swiper (`slidesPerView:
   'auto'` с одной шириной на все карточки) и не создаёт двух разных
   форматов карточек, которые пришлось бы поддерживать отдельно. Если
   принципиально нужен увеличенный featured-слайд — отдельная доработка,
   не блокирует сдачу.

3. **Плавающие виджеты (имя+возраст+аватарка, мини-карточка товара, фото
   товара) — только у первого слайда**, как и в обоих кадрах макета
   (Widget 1/2/3 есть только у первого/активного слайда; карточка-образец
   `669:3819` для остальных слайдов показывает только имя/возраст/цитату
   ЗАПЕЧЁННЫМИ в градиенте, без внешних виджетов). Схема данных
   (`source/pug/data/sReels.json`) поддерживает оба варианта на уровне
   слайда (`person.avatar` есть → плавающие виджеты; нет → текст в
   градиенте) — добавить виджеты другому слайду можно без правки pug/scss.

4. **Цитаты и имена слайдов 2–4 — мок-контент** (как и в `sExpertise`):
   реального текста для этих историй в макете нет (виден только один
   featured-пример + один образец карточки в UI-Kit), остальные слайды
   нужны только чтобы механика слайдера была проверяема на N>1 карточках.
   Заменить на реальные истории при получении от заказчика — см.
   `_slidesNote` в JSON.

5. **Свотч цвета товара — инлайн `style`, не токен.** Цвет свотча
   (`slide.product.colorHex`) — контент товара из данных, а не
   дизайн-токен: используется `style="background-color:${colorHex}"` в pug
   (не в `.scss` блока, поэтому `stylelint declaration-strict-value` его не
   видит и не должен видеть — это те же основания, что и у динамических
   свотчей цвета в будущих `sBestSets`/`sFavorites`, когда они появятся).

6. **Стрелки только от `lg` и выше** — в мобильной ноде `721:2` в
   метаданных нет кнопок-стрелок, только пагинация (буллеты). Общий
   `+ebSliderNav()` рендерит и то, и другое всегда — стрелки скрыты
   локально (`.sReels .eb-slider-nav__arrows { display: none }` до `lg`),
   компонент не трогал.

7. **Full-bleed дорожки формально навешан, эффект нулевой** (тот же случай,
   что описан в `docs/coordination/sExpertise.md`): секция — прямой
   ребёнок `<main>` (полная ширина вьюпорта уже по умолчанию), поэтому
   `@include eb-bleed()` на `.sReels__track` ничего не сдвигает численно.
   Оставлен как защита на случай будущей вложенности; парный
   `eb-bleed-reset()` не понадобился по той же причине, что и там.
   Правый край дорожки долистывается до экрана не vw-трюком, а тем, что
   `.sReels__slider` не имеет `padding-right`, и Swiper сам обрезает
   последний частично видимый слайд по границе секции (граница секции —
   это уже граница вьюпорта).

## Грабля, пойманная только скриншотом (не в §3.1, для остальных карточек с плавающими виджетами)

Первая версия у первого слайда (`.has-badges`) визуально накладывала текст
цитаты на плашку «Александра, 34 года» — на ~23px по вертикали, видно и на
1920, и на 375. Все проверки, кроме скриншота, были зелёными: DOM — оба
элемента на месте, `computed-style` — оба видимы, оверфлоу нет. Причина:
плашка (`.sReels__person`) — плавающий элемент с фикс-геометрией (`bottom:
rem(56)`, высота ~63px), не масштабируется по брейкпоинтам, а цитата —
обычный текст в потоке карточки без запаса под неё. Фикс — резерв
`margin-bottom: rem(132)` у `.sReels__card-quote` именно когда есть плашка
(`.sReels__card.has-badges &__card-quote`). Тот же класс бага, что и
z-index Swiper из §3.1/§6 — «в DOM есть, но перекрыто», просто по другой
причине (геометрия, не стек).

**Побочная находка — вариант граблы §1 (bemto/no-dup-class) через runtime
`class=`, не только через dot-chain.** Первая попытка передать модификатор
через `class=(cond ? 'sReels__card--with-badges' : null)` (полная строка с
`--`) уронила `html-validate` (`no-dup-class`) точно так же, как
dot-chain-версия из грабли: bemto декомпозирует ЛЮБУЮ строку с паттерном
модификатора (`--`), включая переданную через атрибут `class=`, а не только
через `.--mod` в теге. Фикс — обычный (не-BEM) класс `has-badges` без
двойного дефиса; bemto его не трогает. Стоит проверять у любого блока,
где модификатор карточки зависит от данных (условный `class=`), а не
захардкожен в pug.
